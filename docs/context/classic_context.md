### ClassicContext 完整核心机制解析
ClassicContext 是一套**分组多级优先级协程调度上下文**，整体采用「静态资源分组共享 + 实例轻量视图」的顶层架构，核心拆分「任务调度」与「线程同步」双轨独立运行，配合两级并发防护与分层停止机制，支撑多 Processor 线程高效并发调度。

#### 1. 顶层架构：分组共享资源，实例为轻量访问入口
所有核心调度资源均为类静态成员，以 `group_name` 为键一一对应，每个分组拥有一套完整独立的调度资源，组与组之间完全隔离。单个 `ClassicContext` 实例本身不存储队列数据，仅绑定一个分组、持有对应队列与锁的指针，作为 Processor 线程的调度入口视图。

按归属层级可分为两类：
- **组级共享资源**：就绪队列阵列、队列锁阵列、等待互斥锁、条件变量、通知计数器，均按 group 全局唯一，同组所有实例共用。
- **实例私有资源**：`stop_` 原子停止标志、分组名、资源指针，每个实例独立持有，仅作用于当前调度上下文。

#### 2. 核心双轨：就绪队列（rq）与等待同步（wq）职责分离
两套机制各司其职，锁资源完全独立，互不干扰，避免锁竞争扩散：
- **就绪队列（rq = Ready Queue）：负责任务存储与调度选取**
  每个分组包含 20 级优先级的协程队列，每级对应一个 deque 容器存放待执行的 `CRoutine`。采用**优先级级细粒度锁**，每级队列独立配备一把互斥锁，入队、取任务、移除操作仅锁定当前优先级队列，不同优先级的操作可完全并发。对应核心操作：`Enqueue`、`NextRoutine`、`RemoveCRoutine`。

- **等待同步（wq = Wait Queue）：负责线程阻塞与唤醒**
  每个分组共用一套「组级互斥锁 + 条件变量 + 通知计数器」，**不存储协程实体**，仅负责无就绪任务时让 Processor 线程休眠、新任务到来时唤醒线程。锁为组级粗粒度，仅保护通知计数器的读写原子性，不触碰队列数据。对应核心操作：`Wait`、`Notify`、`Shutdown`。

#### 3. 两级并发防护：队列锁保容器，协程锁保执行权
调度体系设计了两层互斥防护，二者保护边界完全不同，缺一不可：
- **第一层：队列级互斥锁**
  即 `rq_locks_` 阵列中的每把锁，仅保护对应优先级 deque 容器本身的结构安全，防止多线程并发增删、遍历时出现迭代器失效、内存损坏。它的持有时间极短，仅在遍历队列、写入/移除元素的瞬间持有，找到目标协程后就会立即释放。

- **第二层：协程级 Acquire/Release 执行互斥**
  每个 `CRoutine` 内置的原子互斥机制，保护单个协程的执行权。这套设计的根源是：协程采用**常驻队列**的方案——协程不会因被调度就从队列中移除，执行完或让出 CPU 后仍留在队列中等待下一轮调度。
  队列锁释放后，其他 Processor 仍可进入同一级队列遍历并拿到同一个协程的指针。如果没有协程级互斥，多个 Processor 会同时执行同一个协程，直接导致协程栈、状态变量完全错乱。

简单总结：队列锁保证「队列容器不被改坏」，协程锁保证「同一个任务不被重复执行」。

#### 4. 分层停止机制：实例级状态标志 + 组级唤醒动作
停止能力拆分为状态标志与执行动作两层，`stop_` 不按分组区分，与 `Shutdown()` 各司其职：
- `stop_` 是**实例级原子状态标志**，每个 `ClassicContext` 实例独立持有，和 group 没有绑定关系。它是调度停止的快速闸门：`NextRoutine` 入口处无锁读取该标志，为 `true` 时直接停止返回任务，仅控制当前实例是否继续取任务，同组其他实例不受影响。
- `Shutdown()` 是**完整停止执行动作**，执行两步流程：先置位当前实例自身的 `stop_`，关闭自身取任务入口；再操作当前绑定分组的组级唤醒机制，将通知计数设为最大值并唤醒所有阻塞的 Processor 线程，让同组所有线程重新检查自身的 `stop_` 状态，推动整个分组的调度线程逐步退出。

#### 5. 完整运作闭环
新协程入队 → 加对应优先级的细粒度队列锁写入队列 → 释放队列锁 → 加组级唤醒锁增加通知计数、唤醒一个等待线程 → Processor 被唤醒 → 从最高优先级到最低优先级逐次加细粒度锁扫描队列 → 尝试获取协程执行权 → 确认就绪后取出执行。

### 为什么 Shutdown 要唤醒所有线程
核心目的是**让同组所有阻塞中的 Processor 线程及时退出等待，实现优雅停机**，避免线程长期挂起、程序无法正常回收资源。具体可以从四层逻辑理解：

#### 1. 背景前提：同组多线程共享同一等待机制
一个 group 通常对应多个 Processor 线程并行调度，无就绪任务时，所有空闲线程都会阻塞在该组的 `cv_wq_` 条件变量上。如果停机时不主动唤醒，这些线程会一直休眠，仅靠 1 秒的超时兜底才会醒来一次，退出效率极低。

#### 2. 为什么用 `notify_all` 而不是 `notify_one`
正常新任务入队调用 `Notify` 时用 `notify_one`，是因为只需要唤醒一个线程处理任务即可。但停机的目标是终止所有调度线程，只唤醒一个的话，其余线程仍会持续阻塞，无法及时响应停止信号。

#### 3. 配合「通知计数设为最大值」的原因
条件变量唤醒后，会通过 `notify_grp_ > 0` 的谓词判断是否真的有事件。如果只做 `notify_all` 但不修改计数，那么多个线程被唤醒后，只有少数能消费到计数，其余线程会因计数归零再次进入阻塞。
直接将 `notify_grp_` 设为 int 最大值，能保证所有被唤醒的线程都能通过谓词检查、顺利退出 `Wait` 函数，不会重新睡回去。

#### 4. 唤醒后的完整退出链路
线程从 `Wait` 醒来后，会再次调用 `NextRoutine` 获取任务；此时若自身 `stop_` 已被置为 `true`，`NextRoutine` 会直接返回 `nullptr`，上层 Processor 检测到空指针后就会退出调度循环，线程正常终止。

> 补充设计细节：`stop_` 是实例级变量，因此完整停机流程中，上层通常会对同组所有 `ClassicContext` 实例依次置位停止标志；而组级的 `notify_all` 保证了所有线程都能及时被唤醒、检查自身停止状态，不会卡在等待中无法退出。
