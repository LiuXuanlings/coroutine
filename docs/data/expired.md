# 数据分发架构两层失效策略设计解析

## 一、核心认知澄清
首先明确：DataDispatcher 与 DataNotifier 采用不同的生命周期管理策略，是基于场景差异的刻意工程权衡，并非资源泄漏或设计疏漏。

**资源泄漏的定义**：程序运行中持续分配资源且永久无法回收，资源占用随时间无限增长，最终导致资源耗尽。本设计不符合该定义：
- 残留条目总量有明确上限，不会无限增长；
- 不会引发崩溃、内存错误等严重问题；
- 换取了热路径性能、接口简洁性与使用心智负担的大幅优化。

两层策略差异的根源：**两层的设计目标、风险等级完全不同**，因此采用差异化的生命周期方案。

## 二、分发层（DataDispatcher）：weak_ptr 自动失效是内存安全刚需
### 设计方案
以 `std::weak_ptr<CacheBuffer>` 存储订阅者缓存，不持有对象所有权。

### 必须采用该方案的原因
分发层最终要执行 `buffer->Fill(msg)` 内存写入操作，属于高风险路径：
1. 若持有强引用：订阅者销毁后缓存对象永久无法释放，造成真正的内存泄漏；
2. 若持有裸指针：对象销毁后写入会触发野指针访问，直接导致进程崩溃，属于严重内存安全事故。

### 失效机制
分发消息时通过 `weak_ptr::lock()` 检测对象存活状态：
- 对象存活：获取临时强引用，保证写入全程对象不被销毁，完成数据写入；
- 对象已销毁：`lock()` 返回空指针，自动跳过该订阅项，从根源规避野指针风险。

### 代价
失效的弱指针会暂留在订阅列表 vector 中，每个条目仅占用8字节指针空间；订阅增删为低频操作，残留总量可控，内存开销可忽略。

## 三、通知层（DataNotifier）：shared_ptr 留存是性能优先的工程取舍
### 设计方案
以 `std::shared_ptr<Notifier>` 存储通知回调对象，持有一份强引用。

> 细节修正：代码中 `if (notifier && notifier->callback)` 属于通用防御式编程，并非用于检测订阅者销毁；实际订阅者销毁后，Notifier 对象本身不会释放，回调依然会完整执行。

### 采用该方案的核心理由
#### 1. 热路径性能优先，避免清理逻辑损伤主路径
`Notify` 是系统最高频的热路径之一，每条消息发布都会触发，其性能直接决定系统延迟。
若实现自动清理死项，两种主流方案都会损伤性能：
- 遍历回调时同步清理：热路径额外增加失效判断、元素移除逻辑，可能触发 vector 内存搬移，引入延迟抖动；
- 提供主动注销接口：移除操作需要加全局写锁，增加销毁路径复杂度与锁开销。

当前设计让热路径保持最纯粹的「遍历-执行」逻辑，将性能压榨到极致，以极少量条目残留为代价。

#### 2. 场景天然适配：订阅增删为极低频操作
该架构面向机器人、自动驾驶等软实时系统，业务特征明确：
- 通道与订阅均为进程启动时创建，运行全程稳定存在，不会高频创建销毁；
- 即使业务节点销毁订阅，系统订阅总量有明确上限，残留条目不会无限增长。

以典型系统为例：200个通道，单通道平均3个订阅，全量销毁后残留600个 shared_ptr 条目，总内存占用不足5KB，对现代系统完全可忽略。

#### 3. 接口极简：实现 RAII 式订阅体验
架构订阅端的设计目标是「构造即订阅，析构即失效」，降低业务层使用成本。
若要求手动调用注销接口，既增加使用心智负担，也容易因遗漏注销引发真实的资源泄漏。当前设计下业务方无需关注注销逻辑，生命周期完全自动管理。

#### 4. 空调用无副作用，风险完全可控
实际框架中，回调绑定的是调度层的 `scheduler.NotifyTask(task_id)` 逻辑：
- 对应协程已销毁时，调度器通过ID查找不到任务，会静默返回false；
- 无效回调仅产生一次「查表未命中」的空操作，无崩溃、无逻辑错误、无资源泄漏，单次开销仅几十纳秒。

### 代价
订阅者销毁后，通知列表中仍保留对象条目，每次通道通知会多执行一次无效回调；因调用极轻量、触发低频，整体开销可接受。

## 四、两层策略对比总结
| 维度 | 分发层（DataDispatcher） | 通知层（DataNotifier） |
| :--- | :--- | :--- |
| 核心风险 | 野指针写入，直接触发进程崩溃（内存安全事故） | 多余一次空函数调用，无安全与逻辑风险 |
| 设计优先级 | 内存安全优先 | 热路径性能 + 接口简洁优先 |
| 存储方案 | `std::weak_ptr` 弱引用，不持有所有权 | `std::shared_ptr` 强引用，延长对象生命周期 |
| 失效逻辑 | `lock()` 失败自动跳过，保障写入安全 | 不做失效检测，回调正常执行，业务侧天然幂等 |
| 残留代价 | 失效弱指针占用微量内存 | 残留 Notifier 对象 + 微量无效回调开销 |

### 核心设计思想
不为零风险场景做过度设计，将复杂度与资源投入集中在真正存在安全风险的路径上，是典型的工业级软件「分级管控、按需设计」的工程思维。
