# Minicyber 数据模块：架构设计与源码深度分析

本文档为 `minicyber` 数据模块提供架构蓝图与源码级深度分析，不仅阐述各组件的功能与交互流程，更深入拆解每一处设计背后的权衡逻辑、潜在问题与工程取舍，同时完整覆盖数据层与调度层的联动机制，还原一套工业级实时通信层的思考路径。

---

## 一、数据模块的核心设计理念

### 1. 协程框架中数据驱动调度的本质价值
在机器人、自动驾驶这类软实时系统中，传统的**时间驱动轮询模型**存在两个不可忽视的缺陷：
- **CPU 资源浪费**：协程持续循环检查通道是否有数据，无数据时也占用 CPU 时间片，负载越高空转损耗越严重；
- **延迟不可控**：轮询周期决定了数据最低延迟，周期短则 CPU 开销大，周期长则延迟高，无法兼顾。

`minicyber` 数据模块的核心价值，是构建了一套**响应式数据驱动调度模型**：
协程无数据时主动让出执行权，进入 `DATA_WAIT` 挂起状态，不占用任何 CPU 资源；仅当对应通道有新数据发布时，才通过通知机制将协程重新标记为就绪、放回调度队列。系统从「主动忙等」转为「被动事件触发」，在低延迟的同时实现了极低的空闲开销。

### 2. 架构设计的四大核心原则
数据模块的所有设计都围绕以下四条原则展开，且每一处代码实现都在践行这些原则：

1.  **发布-订阅完全解耦（匿名通信）**
    发布者只面向 `channel_id` 这个数字抽象发布数据，不需要知道订阅者的数量、位置、执行载体（线程/协程）；订阅者只面向通道订阅，不需要知道发布者是谁、何时发布。两端通过通道 ID 间接关联，生命周期完全独立。

2.  **热路径最小锁竞争**
    严格区分冷热路径：高频的消息分发、通知触发路径，用共享锁、无锁哈希表、快照拷贝等手段将锁持有时间压缩到极致；低频的订阅注册、回调注册路径，才使用独占互斥锁保证安全。

3.  **全链路零拷贝消息传递**
    消息本体以 `std::shared_ptr<T>` 形式封装，从发布者产生到所有订阅者消费，全程只传递智能指针，不发生消息体的深拷贝。底层环形缓冲区存储的也是智能指针，拷贝/移动开销仅为一个指针大小，支撑高吞吐量数据传输。

4.  **职责分层与单向依赖**
    存储、读取语义、路由分发、事件通知、客户端封装被严格拆分为独立层级，上层依赖下层，下层完全不感知上层存在。每一层只解决一个领域的问题，修改、替换某一层不会影响其他层级。

## 二、类划分的底层逻辑与设计深度
数据层共 6 个核心类，调度层配套 4 个核心类，并非随意拆分，每一个类的边界都对应着「变化维度」的隔离。下面从源码视角拆解每个类的核心设计、存在的理由以及容易被忽略的权衡。

### 数据层核心类
| 类名 | 职责定位 | 源码级设计深度与拆分理由 |
| :--- | :--- | :--- |
| **`CacheBuffer<T>`** | 带覆写语义的线程安全环形内存队列 | 纯数据结构层，本质是**固定大小的最新数据滑动窗口**，而非普通消费式队列。采用持续递增的绝对索引而非数组下标对外暴露读写位置，预留 1 个数组空位区分「空」与「满」。<br>核心特性：所有读取操作均不修改内部状态，数据只会被新写入覆盖，不会被消费移除；`Empty()` 仅判断是否从未写入过数据，写入后永久非空。它完全不知道通道、发布者、协程的存在，可被任何需要定长滑动窗口缓存的场景复用。 |
| **`ChannelBuffer<T>`** | 绑定通道 ID 的缓存读取语义层 | 为通用环形缓存赋予业务读取语义，是消费者视角的抽象。封装增量读取、最新读取、批量读取三种模式，并统一处理「消费者掉队自动快进」的边界逻辑。<br>拆分意义：将「怎么存」和「怎么读」分离，存储层替换实现时，读取语义层无需改动；消费者也不需要理解环形缓存的 Head/Tail 原理。<br>所有权说明：Step 14 阶段所有权归 DataDispatcher，演进到 DataVisitor 阶段后，强所有权转移至 DataVisitor，本层为中间持有封装。 |
| **`DataDispatcher<T>`** | 按类型隔离的全局路由分发单例 | 模板单例，每种消息类型对应一个独立实例，天然实现类型隔离。维护「channel_id → 订阅者缓存列表」的路由表，负责将消息一对多写入所有订阅缓存。<br>核心设计：以 `std::weak_ptr` 存储订阅缓存，实现发布者与订阅者生命周期解耦；采用**快照式读 + 提前放锁**的并发策略，既提升分发吞吐量，又从根源规避回调重入死锁。<br>演进路标：当前 `shared_mutex + unordered_map` 为 Step 14 过渡实现，后续 Step 26 将替换为无锁 `AtomicHashMap`。 |
| **`DataNotifier`** | 全局无锁事件通知中心 | 全局唯一单例，与数据类型无关，是数据层与调度层的唯一对接点。专门维护「channel_id → 唤醒回调列表」。<br>核心设计：冷热路径分离——低频的注册加互斥锁，高频的通知路径使用 `AtomicHashMap` 无锁查找，最大化降低通知开销。它完全不感知数据内容，只负责事件唤醒。 |
| **`DataVisitorBase`** | 订阅者公共能力基类 | 抽离单通道订阅者通用的通知对象管理与回调注册能力，持有 `Notifier` 实例与全局通知器指针。消费游标 `next_msg_index_` 为保护成员，供子类增量读取场景使用。 |
| **`DataVisitor<T>`** | 单通道订阅的客户端门面 | 继承 `DataVisitorBase`，整合「缓存持有 + 消费进度维护 + 通知注册 + 协程挂起」全套能力，是业务代码直接使用的入口。<br>核心设计：双接口分层——纯非阻塞的 `TryFetch` 适配自定义调度场景，阻塞式的 `Fetch` 封装协程等待逻辑，兼顾灵活性与易用性。构造即订阅、析构即失效，RAII 风格管理生命周期。 |
| **`DataFusion<T1, T2>`** | 双通道 AllLatest 屏障融合器 | 采用**组合模式**复用两个 `DataVisitor` 实例，不直接继承 `DataVisitorBase`，独立维护融合级进度。实现双路数据的屏障同步：两路都有新数据时才输出融合结果。<br>核心设计：不复用 `DataVisitor::TryFetch` 做增量读取，而是直接操作底层缓存、独立维护融合级尾指针，从根源避免「单路游标提前推进导致数据丢失」的经典问题；采用轮询式唤醒而非精确计数，用可忽略的性能开销换取实现简洁性。 |

### 调度层配套核心类（数据驱动联动层）
| 类名 | 职责定位 | 核心设计点 |
| :--- | :--- | :--- |
| **`Scheduler`** | 顶层调度器门面 | 整合工作线程与调度上下文，提供任务创建、唤醒、停止接口。采用轮询策略将任务分发到各 Processor 逻辑本地队列，维护 task_id 到协程对象的全局映射。 |
| **`Processor`** | 工作线程封装 | 每个实例持有一个工作线程与一个调度上下文，循环执行「取任务→恢复协程→让出」的调度流程，支持延迟启动与优雅退出。 |
| **`ClassicContext`** | 多级优先级调度上下文 | 继承 `ProcessorContext`，按 group 组织静态共享的 20 级优先级队列。Scheduler 为每个 Processor 分配独立 group，实现逻辑上的本地队列；同时天然支持跨 group 工作窃取。通过唤醒计数器 + 条件变量实现线程阻塞与唤醒，过滤虚假唤醒。 |

### 类拆分的深层价值
1.  **可测试性**：最底层的 `CacheBuffer` 是纯数据结构，不依赖协程、调度器，可以独立做单元测试；越上层依赖越多，但测试用例可以逐层叠加，符合金字塔测试原则。
2.  **生命周期安全**：通过强/弱引用的分层持有，天然避免循环引用。订阅者对象销毁时，底层缓存自动释放，分发器自动跳过失效项，无需手动注销，也不会出现野指针。
3.  **可演进性**：未来如果要替换无锁缓存、更换调度模型、支持多进程通信，都只需要修改对应层级，上层业务代码零感知。

### 1. 层次与依赖方向
严格遵循**自上而下单向依赖**，绝不反向依赖：
- **门面层**：`DataVisitor<T>` / `DataFusion<T1, T2>`，业务协程直接调用；
- **路由与通知层**：`DataDispatcher<T>` / `DataNotifier`，负责全局路由与事件分发；
- **抽象读取层**：`ChannelBuffer<T>`，封装读取语义与边界处理；
- **核心存储层**：`CacheBuffer<std::shared_ptr<T>>`，最底层的内存容器；
- **调度联动层**：`Scheduler` / `ClassicContext` / `Processor`，接收通知事件并完成协程唤醒调度。

### 2. 两种单例的设计对比
架构中设计了两种不同形态的单例，对应不同的隔离需求：
- **模板单例（`DataDispatcher<T>`）**：每个消息类型对应一个独立的分发器实例，不同类型数据的路由表完全隔离，天然保证类型安全，避免不同数据类型互相干扰。
- **全局单例（`DataNotifier`）**：所有数据类型共用同一个通知中心，仅通过 `channel_id` 区分通道。因为唤醒逻辑与数据类型无关，统一单例可以减少冗余，简化调度层对接。

### 3. 所有权链路（强/弱引用分布）
这是这套架构生命周期安全的核心，也是最容易理解不到位的地方：
1.  **强所有权链**：`DataVisitor` → 组合持有 `ChannelBuffer` → 强引用 `CacheBuffer`。
    订阅者持有的 `DataVisitor` 对象是缓存的真正所有者，只要它活着，底层缓存就不会释放。
2.  **弱观察关系**：`DataDispatcher` → 以 `std::weak_ptr` 引用 `CacheBuffer`。
    分发器只观察缓存是否存活，不持有所有权，既避免循环引用，也保证订阅者销毁时缓存能正常释放。
3.  **通知对象所有权**：`DataVisitorBase` 强持有 `Notifier` 对象，`DataNotifier` 中也以 `shared_ptr` 存储回调。
    订阅者销毁时通知对象引用计数减一，通知中心遍历会自动跳过空指针，和分发层的弱引用设计思路一致。

### 4. 两端自动失效策略对比
分发层与通知层分别采用了不同的「无需主动注销」设计，都是用极低成本换取接口简化：
| 层级 | 实现方案 | 失效机制 | 代价 |
| :--- | :--- | :--- | :--- |
| 分发层（DataDispatcher） | `std::weak_ptr` 存储缓存 | 订阅者销毁后 `lock()` 返回空指针，自动跳过写入 | 失效指针暂留 vector 中，占用少量内存；订阅增删低频，可接受 |
| 通知层（DataNotifier） | `std::shared_ptr` 存储 Notifier | 订阅者销毁后对象引用计数降低，但列表中仍保留条目；回调执行时判空跳过 | 存在少量无效回调调用开销；通知本身为轻量操作，可接受 |

### 5. 核心耦合点
- **组合强耦合**：`DataVisitor` 与 `ChannelBuffer` 是强组合关系，这是合理的——订阅者必然依赖缓存，不存在没有缓存的订阅者。
- **初始化时耦合**：`DataVisitor` 构造时向 `DataDispatcher` 和 `DataNotifier` 注册，属于初始化期的时序耦合，运行期无直接依赖，符合开闭原则。
- **通道 ID 纽带**：`channel_id` 是贯穿分发、通知、缓存的唯一关联标识，三层之间只通过 ID 匹配，不直接持有对方指针。

## 四、典型业务场景与选型逻辑
### 场景一：单通道流式数据处理（如传感器驱动 → 算法节点）
- **场景描述**：激光雷达驱动以固定频率发布点云帧，检测算法协程按顺序逐帧处理，优先保证数据新鲜度，消费跟不上时自动跳过旧帧。
- **接口选型**：使用 `DataVisitor::Fetch()` 增量读取。
- **运行逻辑**：驱动调用 `Dispatch` 发布点云，算法协程从 `Fetch` 挂起中被唤醒，读取一帧并推进消费索引，处理完成后再次进入等待。消费者速度跟不上时，环形缓存自动覆盖旧帧，`Fetch` 检测到掉队后自动快进到最新帧，保证算法始终处理最新数据。

### 场景二：单通道状态采样（如实时状态读取）
- **场景描述**：监控节点周期性读取某个通道的最新状态，不需要维护连续消费进度，只需要每次拿到当前最新值。
- **接口选型**：使用 `ChannelBuffer::Latest()` 或 `DataVisitor` 封装的快照读取。
- **运行逻辑**：直接读取缓存尾部最新数据，不修改任何消费游标，完全不影响其他订阅者的增量消费。

### 场景三：多通道传感器融合（如相机 + 雷达融合跟踪）
- **场景描述**：融合节点需要同时拿到相机图像和雷达目标，才能执行融合跟踪算法，缺一路都无法运行。
- **接口选型**：使用 `DataFusion::WaitForAllLatest()` 屏障式读取，AllLatest 语义。
- **运行逻辑**：融合协程调用 `WaitForAllLatest`，任意一路为空就挂起；任意一路有新数据到达都会触发唤醒，重新检查两路状态；直到两路都有新数据，才返回各自的最新帧进入融合逻辑。
- **选型考量**：选择 AllLatest 语义而非逐条对齐，是因为传感器频率通常不一致，优先保证融合结果的实时性，而非严格的帧一一对应。

## 五、核心链路源码级逐行拆解
### 场景 A：单通道发布-消费全流程
#### 1. 消息发布：`DataDispatcher::Dispatch`
这是整个分发层最核心的函数，每一处设计都对应着并发与性能的权衡：
```cpp
BufferVector snapshot;
{
  std::shared_lock<std::shared_mutex> lock(buffers_map_mutex_);
  auto it = buffers_map_.find(channel_id);
  if (it == buffers_map_.end()) return false;
  snapshot = it->second;
}
```
- **快照式读取 + 即时放锁**：仅在查找、拷贝订阅列表时持有共享读锁，拷贝完成立即释放。
  - 规避重入死锁：后续写缓存、触发通知都不持有 map 锁，即使回调中再次调用 `Dispatch` 或 `AddBuffer`，也不会因同一线程持有锁而死锁——这是最容易踩的坑：`std::shared_mutex` 不支持递归加锁，持有读锁时申请写锁会直接永久阻塞。
  - 缩小锁粒度：耗时的批量写缓存、唤醒协程操作全部移出锁外，多线程分发不同通道时几乎无竞争。
  - 可接受的一致性牺牲：仅拷贝 weak_ptr 集合，开销极低；订阅增删是低频操作，快照与实时状态的短暂不一致只影响单次分发，下一次即可恢复，属于最终一致。

```cpp
for (auto& buffer_wptr : snapshot) {
  if (auto buffer = buffer_wptr.lock()) {
    std::lock_guard<std::mutex> lg(buffer->Mutex());
    buffer->Fill(msg);
  }
}
```
- **弱引用自动失效**：`lock()` 一步完成两件事：
  1. 获取临时强引用，保证 `Fill` 写入全程缓存对象不会被并发销毁；
  2. 自动过滤已销毁的缓存，`lock()` 返回空则跳过，无需单独的注销接口。
- **分层锁设计**：map 锁只保护路由表，每个缓存自己的锁保护数据写入。锁粒度从全局降到单个缓存，并发写入不同缓存时互不阻塞。

最后调用 `notifier_->Notify(channel_id)` 触发通知，此时全程不持有任何分发层锁。

#### 2. 数据写入：`CacheBuffer::Fill`
覆盖式环形缓存的核心逻辑：
- 缓存未满时：写入 `tail_ + 1` 位置，tail 后移；
- 缓存已满时：直接覆盖 `head_` 位置的最旧数据，head 和 tail 同时后移，窗口大小保持不变。
- 设计本质：永远保留最新的 N 条数据，旧数据自动淘汰，适配实时系统「新数据优先」的诉求。
- 关键特性：写入只推进绝对索引，索引永不归零；所有读取操作均为只读，不修改缓存内部状态。

#### 3. 事件通知：`DataNotifier::Notify`
热路径无锁设计：通过 `AtomicHashMap` 无锁查找到通道对应的回调列表，遍历执行回调。整个过程不加全局锁，多线程并发通知不同通道时完全并行，是高吞吐量的关键保障。

#### 4. 调度层唤醒：从回调到协程就绪
DataNotifier 触发的回调本质是调度层注入的唤醒逻辑，完整执行链路：
1.  回调调用 `Scheduler::NotifyTask(crid)`，通过全局 ID 映射找到对应协程对象；
2.  标记协程更新标志，将协程状态从 `DATA_WAIT` 转为可调度状态；
3.  调用 `ClassicContext::Enqueue(cr)` 将协程放入对应优先级的就绪队列；
4.  调用 `ClassicContext::Notify(group_name)`，递增该 group 的 `notify_grp_` 唤醒计数器，同时通过条件变量唤醒阻塞的工作线程。

> 补充设计细节：`notify_grp_` 计数器的核心作用是**过滤条件变量虚假唤醒**。`Wait()` 被唤醒后会先检查计数器是否大于 0，有未消费的通知才去尝试取任务，否则继续等待，避免无效的队列扫描开销。

#### 5. 协程恢复与消费：`DataVisitor::Fetch`
```cpp
while (!TryFetch(m)) {
  auto rt = CRoutine::GetThis();
  rt->SetState(RoutineState::DATA_WAIT);
  CRoutine::Yield(RoutineState::DATA_WAIT);
}
```
- 循环调用非阻塞的 `TryFetch`，失败则主动让出协程，进入等待状态；
- 协程被调度器唤醒后自动重试，直到拿到数据返回。

`TryFetch` 内部调用 `ChannelBuffer::Fetch`，完成三层边界处理：
1.  首次读取（索引为 0）：直接定位到最新数据；
2.  消费掉队（索引小于 Head）：自动快进到最新位置，跳过被覆盖的旧数据；
3.  已追平（索引等于 Tail+1）：返回 false，无新数据。

读取成功后，`next_msg_index_` 自增，消费进度自动推进。

### 场景 B：双通道融合屏障流程
#### 1. 核心设计：为什么不直接调用 `dv1_.TryFetch()` + `dv2_.TryFetch()`
这是 `DataFusion` 最深刻的设计决策，也是新手最容易写错的地方：
如果先调用 ch1 的 `TryFetch`，成功后游标不可逆推进；再调用 ch2 的 `TryFetch` 失败，就会出现「ch1 数据被消费了但融合失败」的情况——下一次 ch2 数据到达时，ch1 的游标已经追平，永远凑不齐两路数据，ch1 的消息永久丢失。

因此 `TryAllLatest` 选择**直接操作底层 CacheBuffer，不使用单路增量接口，独立维护融合级进度**。

#### 2. `TryAllLatest` 源码级拆解
```cpp
std::unique_lock<std::mutex> lk1(mtx1, std::defer_lock);
std::unique_lock<std::mutex> lk2(mtx2, std::defer_lock);
std::lock(lk1, lk2);
```
- **为什么必须同时加两把锁**：保证读取的 `Tail` 索引和 `Back` 数据是一致的原子快照，避免读到一半缓存被写入更新，出现「Tail 是新的、数据是旧的」不一致状态。
- **死锁规避原理**：使用 `std::lock` 同时获取两把锁，内部会按全局固定顺序加锁，彻底避免因不同场景加锁顺序不一致导致的哲学家就餐死锁，是多资源操作的标准安全写法。

```cpp
if (tail1 == last_fused_tail1_ && tail2 == last_fused_tail2_) {
  return false;
}
```
- **融合级去重**：用两路的 Tail 索引标记上一次融合的位置，只有至少一路 Tail 前进了，才认为有新的融合结果。既避免重复返回相同数据，也天然适配 AllLatest 语义——每次都取两路最新，中间数据自动跳过。

#### 3. 轮询式屏障的取舍
`DataFusion` 采用「任意一路更新就唤醒，没凑齐就再挂起」的轮询策略，而非「两路都更新才唤醒」的精确屏障：
- **优点**：实现简单，不需要维护通知计数，鲁棒性强，不会因为计数异常导致永久挂起；
- **代价**：存在少量无效唤醒，每次无效唤醒仅执行一次双锁检查 + 一次协程切换，开销极低，对于实时系统完全可接受。

## 六、工程亮点与设计权衡总结
| 技术点 | 实现方式 | 解决的问题 | 设计权衡 |
| :--- | :--- | :--- | :--- |
| **无锁热路径通知** | `AtomicHashMap` 实现 Notify 读路径无锁，AddNotifier 冷路径加锁 | 避免通知成为全局性能瓶颈，支撑高并发分发 | 哈希表容量固定，不支持动态扩容，适合通道数可预估的场景 |
| **快照式分发** | shared_mutex 共享锁下拷贝订阅列表，立即放锁后再写入+通知 | 缩小锁粒度，规避回调重入死锁 | 存在极短暂的订阅列表不一致，低频场景可接受 |
| **弱引用生命周期管理** | Dispatcher 存 weak_ptr，分发时 lock 检查有效性 | 解耦发布订阅生命周期，避免循环引用，无需注销接口 | 失效指针暂留 vector 中不清理，占用极少量内存，换热路径性能 |
| **死锁避免多锁** | `std::defer_lock` + `std::lock` 同时加双锁 | 解决多通道操作的锁顺序死锁问题 | 无明显代价，属于标准最佳实践 |
| **掉队自动快进** | ChannelBuffer::Fetch 检测索引小于 Head 则快进到 Tail | 防止慢消费者拖垮系统、避免索引越界 | 会丢失旧数据，不适合要求严格保序、不丢消息的场景 |
| **双接口分层设计** | TryFetch 纯非阻塞 + Fetch 协程阻塞封装 | 同时满足自定义调度灵活性与业务代码易用性 | 无明显代价，属于接口分层的标准范式 |
| **唤醒计数器防虚假唤醒** | notify_grp_ 计数 + 条件变量，唤醒后先检查计数 | 避免条件变量虚假唤醒导致的无效队列扫描 | 无明显代价，极小内存开销换稳定性 |
| **模板单例+全局单例搭配** | DataDispatcher 按类型模板单例，DataNotifier 全局单例 | 兼顾类型安全与统一调度入口，减少冗余 | 无明显代价，属于架构精细化设计 |
| **覆盖式滑动窗口缓存** | 绝对索引单调递增，新数据覆盖旧数据，读取不修改状态 | 保障数据新鲜度，简化多订阅者并发读取 | 不支持严格保序、不丢消息的场景 |

## 七、整体总结与架构边界
### 1. 架构核心优势
- **高性能**：热路径无锁/轻锁、零拷贝消息传递、锁粒度极致压缩，在高消息速率下依然保持低开销；
- **高可靠**：分层锁设计、弱引用生命周期管理、掉队自修复机制、防虚假唤醒设计，在并发场景下依然保持稳定，不会出现野指针、死锁、消费卡死等问题；
- **低耦合**：业务层仅需和 `DataVisitor` / `DataFusion` 交互，完全感知不到底层调度、存储、分发的实现细节，替换底层组件不影响业务。

### 2. 架构边界与适用场景
这套架构是为**软实时、高吞吐、数据新鲜度优先**的场景设计的，有明确的适用边界：
- ✅ 适合：机器人、自动驾驶的传感器数据传输，实时控制系统的状态同步，多协程数据驱动调度；
- ❌ 不适合：要求严格不丢消息、严格保序的业务（如金融交易、可靠日志传输），因为覆盖式缓存和掉队快进本质上是「丢旧保新」的策略。

### 3. 可演进方向
- **进程间扩展**：当前为单进程内存内通信，可扩展共享内存传输层，在不改变上层接口的前提下支持多进程通信；
- **分发层无锁化升级**：`DataDispatcher` 当前使用 `shared_mutex`，后续可按路标替换为无锁哈希表，进一步提升分发吞吐量；
- **融合能力扩展**：当前仅支持双通道 AllLatest，可扩展为 N 通道融合、时间戳对齐融合等更复杂的融合语义；
- **工作窃取优化**：当前 ClassicContext 已预留工作窃取能力，可进一步完善窃取策略，提升多核负载均衡能力。
