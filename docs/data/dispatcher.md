# 数据分发架构整体设计梳理
## 一、架构总览
这是一套**分层解耦的发布-订阅式数据分发系统**，面向实时系统场景设计，核心解决「多发布者→多订阅者」的一对多消息路由问题，同时兼顾并发安全、生命周期解耦、低延迟分发与容错降级。

整体自下而上分为四层，严格遵循单向依赖原则：上层依赖下层，下层完全不感知上层存在。四层分别对应四个独立的技术领域：**存储层 → 读取语义层 → 分发路由层 → 唤醒通知层**。

---

## 二、分层详解（自底向上）
### 第一层：CacheBuffer<T> —— 通用环形存储层
**定位**：纯数据结构层，带互斥锁的定长可覆盖环形缓冲区，完全不感知业务逻辑，是最底层的存储容器。

#### 核心能力
1. 基于 vector 实现环形存储，预留 1 个空位区分「空」与「满」；构造传入的 size 为有效容量，底层实际大小为 `size + 1`。
2. 使用**持续递增的绝对索引**（而非数组下标）对外暴露读写位置：
   - `Head()`：当前缓存中最早有效数据的绝对索引（`head_ + 1`，`head_` 指向最早元素的前一个位置）
   - `Tail()`：当前缓存中最新有效数据的绝对索引
   - `Size() = tail_ - head_`
3. 覆盖式写入：缓存满时自动覆盖最旧数据，head 和 tail 同步后移，始终保持滑动窗口。
4. 自带互斥锁，自身保证并发读写安全。

#### 设计价值
- 通用复用：与通道、订阅、分发完全解耦，所有需要「定长滑动窗口缓存」的场景都可使用。
- 封装细节：环形下标换算、覆盖逻辑、锁管理全部内部实现，上层无需关心存储原理。
- 替换成本低：后续更换无锁缓存、内存池等方案，仅需修改本层，上层业务零改动。

---

### 第二层：ChannelBuffer<T> —— 单订阅者读取视图层
**定位**：单个订阅者专属的「通道绑定 + 读取语义封装」，是订阅者直接操作的入口，为底层通用缓存赋予业务语义。

#### 核心能力
1. 绑定唯一 `channel_id`，标识所属数据通道。
2. 封装三种业务读取策略，统一处理边界场景：
   - `Fetch(index, msg)`：按消费进度增量读取，`index` 为输入输出参数
     - `index == 0`：首次读取，直接取最新数据
     - `index == Tail + 1`：已追平最新数据，返回 false
     - `index < Head`：消费掉队（旧数据被覆盖），自动快进到最新位置，跳过丢失数据
     - 正常区间：返回对应索引数据
   - `Latest(msg)`：直接获取最新一条数据，不关心历史进度
   - `FetchMulti(size, vec)`：批量获取最新 N 条数据，按时间正序返回
3. 底层存储 `std::shared_ptr<T>`，全程引用传递，零拷贝且避免对象切片。

#### 设计价值
- 隔离存储实现：订阅者无需理解环形缓存的 Head/Tail 逻辑，不用自行处理越界、掉队等边界。
- 统一业务策略：「实时优先、掉队自动快进」的实时系统策略集中实现，避免每个订阅者重复开发。
- 明确生命周期边界：缓存的强所有权归 ChannelBuffer 持有，订阅者销毁则缓存强引用释放。

> 关键特性：**一个通道对应多个 ChannelBuffer 实例**，每个订阅者独立持有一份缓存，各自维护消费进度，互不干扰。

---

### 第三层：DataDispatcher<T> —— 通道级分发路由层
**定位**：按消息类型隔离的全局单例分发器，维护「channel_id → 订阅者缓存列表」的路由映射，是发布者与订阅者之间的桥梁。

#### 核心能力
1. 模板单例：每种消息类型 T 对应一个独立的分发器实例，不同类型数据天然隔离。
2. 订阅注册：`AddBuffer` 将订阅者的缓存注册到对应通道的列表中。
3. 消息分发：`Dispatch` 将消息广播写入该通道所有有效订阅缓存，完成后触发通知。
4. 生命周期弱管理：仅存储 `std::weak_ptr<CacheBuffer>`，不持有强所有权。

#### 关键并发与生命周期设计
1. **读写锁分层控制**：使用 `shared_mutex` 保护路由表
   - 适配读多写少场景：分发（读）用共享锁，注册（写）用独占锁。
   - 快照式读取：仅在拷贝缓存列表时持有锁，拷贝完成立即释放，再执行写入与通知
     - 规避重入死锁：回调中再次调用分发器接口时，不会因自身持有锁而死锁
     - 缩小锁粒度：耗时的写缓存、发通知操作不占用路由表锁，提升并发吞吐量
     - 成本可接受：仅拷贝 weak_ptr 指针集合，开销极低；订阅增删为低频操作，短暂不一致可接受
2. **弱引用自动失效**：遍历缓存时通过 `weak_ptr::lock()` 获取强引用
   - 自动过滤死项：ChannelBuffer 销毁后强引用归零，`lock()` 返回空指针则自动跳过，无需主动注销接口
   - 写入安全保障：获取强引用后，写入全程缓存对象不会被并发销毁

#### 设计价值
- 发布订阅解耦：发布者仅需调用 Dispatch，无需感知订阅者数量、身份与读取逻辑。
- 生命周期解耦：避免循环引用，订阅者销毁自动失效，简化接口设计。
- 并发策略封装：锁粒度、重入防护、快照方案全部收敛在本层，上层无感知。

---

### 第四层：DataNotifier —— 全局唤醒通知层
**定位**：独立的事件通知中心，是数据层与协程调度层的对接点，专门负责数据到达后的线程/协程唤醒。

#### 核心能力
1. 全局单例，维护「channel_id → 回调列表」的映射。
2. `AddNotifier`：向指定通道注册通知回调（冷路径，加互斥锁保护）。
3. `Notify`：触发指定通道的所有回调（热路径，基于 AtomicHashMap 无锁读取，性能优先）。

#### 设计价值
- 关注点分离：数据分发与调度唤醒完全解耦
  - DataDispatcher 只关心数据存到哪，不关心谁在等数据
  - DataNotifier 只关心唤醒谁，不关心数据内容与存储
- 易扩展：后续更换唤醒机制（协程→线程池→事件fd），仅需修改本层，分发逻辑完全不受影响。

## 三、层间耦合关系与纽带
### 1. 依赖方向（严格单向）
`DataNotifier` ← `DataDispatcher` ← `ChannelBuffer` ← `CacheBuffer`
- 上层调用下层接口，下层完全不感知上层存在。
- 每层仅和直接下层交互，不跨层调用。

### 2. 三大核心纽带
| 纽带 | 作用 | 贯穿层级 |
|------|------|----------|
| **channel_id（通道ID）** | 全局唯一标识一条数据流，是路由匹配的核心依据 | ChannelBuffer、DataDispatcher、DataNotifier 三层 |
| **shared_ptr / weak_ptr** | 管理缓存对象生命周期，实现所有权与观察权分离 | CacheBuffer（被持有）→ ChannelBuffer（强所有权）→ DataDispatcher（弱观察） |
| **类型参数 T** | 定义消息数据类型，保证类型安全 | CacheBuffer、ChannelBuffer、DataDispatcher 三层；DataNotifier 与数据类型无关 |

---

## 四、核心设计思想汇总
1. **单一职责原则**：每层只做一件事，边界清晰，修改影响不扩散。
2. **读写分离与锁粒度最小化**
   - 热路径无锁/轻锁（分发用共享锁、通知无锁）
   - 冷路径加锁（注册用独占锁）
   - 锁持有时间压缩到最短，耗时操作全部移出锁外
3. **生命周期解耦**
   - 所有权与观察权分离，用 weak_ptr 避免循环引用
   - 对象销毁自动失效，无需显式注销接口，简化使用
4. **实时系统优先**
   - 消费掉队不阻塞，自动快进保障最新数据
   - 覆盖式缓存，始终保留最新数据窗口
   - 低延迟分发，锁开销最小化
5. **容错降级**
   - 失效订阅自动跳过，不影响整体分发
   - 快照短暂不一致可接受，保障主路径性能

## 五、完整运行链路
### 1. 订阅注册链路
订阅者创建 `ChannelBuffer`（持有 CacheBuffer 强引用）→ 调用 `DataDispatcher::AddBuffer` 注册 → 分发器将缓存的 weak_ptr 存入对应 channel 的路由表。
订阅者同时向 `DataNotifier` 注册回调，关联同一个 channel_id。

### 2. 消息发布链路
发布者调用 `DataDispatcher::Dispatch(channel_id, msg)`
1. 加共享锁，从路由表中拷贝该通道的缓存列表快照，立即释放锁；
2. 遍历快照，逐个 lock 获取强引用，有效则加缓存锁写入消息；
3. 写入完成后，调用 `DataNotifier::Notify(channel_id)` 触发所有注册回调，唤醒等待的协程/线程。

### 3. 消息消费链路
订阅者被唤醒后，调用自身 `ChannelBuffer` 的读取接口：
- 增量消费：调用 Fetch，传入上次消费索引，获取新数据并更新索引；
- 状态查询：调用 Latest 直接取最新值；
- 批量处理：调用 FetchMulti 获取一段历史数据。

### 4. 订阅销毁链路
订阅者销毁 `ChannelBuffer` → CacheBuffer 强引用计数归零 → 缓存对象析构。
后续分发时，`weak_ptr::lock()` 返回空，自动跳过该订阅者，无需主动注销。

## 六、关键设计权衡
1. **为什么用 weak_ptr 而不是主动注销？**
   简化接口，避免忘记注销导致的内存泄漏与野指针；代价是 vector 中残留失效指针，但订阅增删低频，可接受。

2. **为什么要做快照、提前释放锁？**
   核心是防止回调重入引发死锁，其次是提升并发性能；代价是快照与实时状态短暂不一致，低频场景可接受。

3. **为什么用绝对索引而不是数组下标？**
   便于消费者维护消费进度，直观判断掉队、追平等状态；环形换算封装在底层，上层无需关心。

4. **为什么分发和通知要分成两层？**
   关注点分离，数据路由和调度唤醒是两个独立领域，各自迭代互不影响。
