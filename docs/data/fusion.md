# DataFusion 设计详解
`DataFusion<T1, T2>` 是**双通道屏障式数据融合器**，实现「AllLatest（全量最新）」融合语义：只有当两个通道都有数据时，才输出两路各自的最新消息。它完全复用 `DataVisitor` 的订阅、通知、缓存能力，同时从设计上规避了「单路游标提前推进导致数据丢失」的问题，是面向多通道同步消费的顶层封装。

---

## 一、整体定位与核心特性
它对应单通道的 `DataVisitor`，专门解决双路数据同步消费的场景，核心设计点：
1. **屏障语义**：两路数据都就绪才返回结果，任意一路为空都不输出；
2. **AllLatest 语义**：每次成功融合都返回两路各自的最新数据，不保证逐条消息对齐，优先保障数据新鲜度，适合实时状态融合场景；
3. **能力复用**：内部持有两个 `DataVisitor` 实例，天然继承通道缓存、分发注册、通知唤醒的全套能力，无需重复实现底层逻辑；
4. **双接口对齐**：和 DataVisitor 保持一致的接口风格，提供非阻塞的 `TryAllLatest` 和协程阻塞的 `WaitForAllLatest`，使用体验统一。

## 二、核心实现逐解
### 1. 构造与唤醒回调：单回调绑定双路
```cpp
DataFusion(const VisitorConfig& cfg1, const VisitorConfig& cfg2)
    : dv1_(cfg1), dv2_(cfg2) {}

void RegisterWakeCallback(std::function<void()> callback) {
  auto cb = std::make_shared<std::function<void()>>(std::move(callback));
  dv1_.RegisterNotifyCallback([cb]() { (*cb)(); });
  dv2_.RegisterNotifyCallback([cb]() { (*cb)(); });
}
```
- **RAII 式订阅**：构造函数直接创建两个 DataVisitor，自动完成两路的缓存注册、通知注册，对象生命周期与订阅周期绑定。
- **共享唤醒回调**：用 `shared_ptr` 包装同一份回调函数，分别绑定到两个通道的通知器上。**任意一路有新数据发布，都会触发同一个唤醒回调**，让挂起的协程重新检查两路状态。
- 这就是「轮询式屏障」的实现基础：不需要精确计数通知次数，只要有一路更新就唤醒检查，没凑齐就继续挂起。

### 2. TryAllLatest：非阻塞融合核心（解决游标问题的关键）
这是整个类最核心的设计，彻底避开了之前「单路 TryFetch 成功后游标前进、另一路失败导致数据丢失」的问题。

#### 核心思路
**不使用 DataVisitor::TryFetch，不推进单路的消费游标，而是在融合层独立维护整体进度**：
- 直接访问底层 `CacheBuffer`，读取两路的最新尾指针 `Tail` 和最新数据 `Back`；
- 用 `last_fused_tail1_ / last_fused_tail2_` 记录上一次成功融合时两路的尾指针位置；
- 只有当「两路都非空」且「至少一路的尾指针有更新」时，才返回最新数据并更新融合进度。

#### 执行步骤拆解
##### ① 双锁安全加锁
```cpp
std::unique_lock<std::mutex> lk1(mtx1, std::defer_lock);
std::unique_lock<std::mutex> lk2(mtx2, std::defer_lock);
std::lock(lk1, lk2);
```
- 同时操作两个独立缓存，必须同时持有两把锁，保证读取的尾指针和数据是一致的快照，不会读到一半另一路被写入更新，导致状态不一致。
- `std::defer_lock` + `std::lock` 是 C++ 标准的多锁死锁规避写法：它会按全局固定顺序加锁，避免因不同场景加锁顺序不一致导致的死锁。

##### ② 基础屏障判断
```cpp
if (cb1->Empty() || cb2->Empty()) {
  return false;
}
```
任意一路没有数据，直接返回失败，不满足融合的前置条件。

##### ③ 融合进度判断
```cpp
if (tail1 == last_fused_tail1_ && tail2 == last_fused_tail2_) {
  return false;
}
```
如果两路的尾指针都和上次融合时完全一致，说明没有任何新数据，直接返回“已追平”，避免重复返回相同数据。
只要至少一路有更新，就认为可以产生新的融合结果。

##### ④ 提交融合结果
```cpp
last_fused_tail1_ = tail1;
last_fused_tail2_ = tail2;
msg1 = cb1->Back();
msg2 = cb2->Back();
```
更新融合进度标记，取出两路最新数据返回。

#### 为什么能解决之前的游标丢失问题？
之前的问题根源是「单路读取成功就不可逆地推进了单路消费游标」，而这个实现里：
- 单路 DataVisitor 的 `next_msg_index_` 全程没有被使用、没有被修改；
- 进度是融合层面的整体进度，只和“是否产生过融合结果”绑定，不会出现单路前进、另一路没跟上导致数据丢失的情况；
- 每次都取最新数据，天然适配 AllLatest 语义。

### 3. WaitForAllLatest：协程阻塞版本
和 `DataVisitor::Fetch` 逻辑完全对齐：循环调用非阻塞接口，失败就将协程置为 `DATA_WAIT` 状态并让出执行权，等待下一次唤醒后重试。
必须在协程上下文中调用。

## 三、关键设计权衡
### 1. 轮询式屏障 vs 精确屏障
- 选择了**轮询式屏障**：任意一路有数据都唤醒，没凑齐就再挂起。
- 优点：实现简单，不需要维护通知计数状态，鲁棒性强；
- 代价：存在少量无效唤醒（只有一路更新时的空检查），但开销极低，仅一次双锁检查 + 一次协程切换，对于实时系统完全可接受。

### 2. AllLatest 语义 vs 逐条保序融合
- 选择了**AllLatest 语义**：每次都取两路最新，中间数据可能被跳过。
- 适用场景：传感器状态融合、最新状态对齐等实时场景，优先保证数据新鲜度；
- 如果需要严格逐条对齐（比如每帧数据必须一一对应），则需要额外的对齐缓存和匹配逻辑，复杂度会大幅上升。

### 3. 复用 DataVisitor 的收益与取舍
- 收益：自动获得缓存管理、分发注册、通知唤醒的全套能力，代码复用度高，和单通道订阅逻辑保持架构一致；
- 取舍：DataVisitor 的 TryFetch/Fetch 增量消费接口在融合场景中没有被使用，属于“带进来但不用”的能力，但换来的是架构一致性和开发效率，利大于弊。

---

## 四、在整体架构中的位置
它和 DataVisitor 同属**订阅者顶层封装层**，下层依然依赖 DataDispatcher、DataNotifier、ChannelBuffer、CacheBuffer 四层基础能力，只是把单路订阅扩展成了双路融合订阅，向上给业务层提供开箱即用的多通道同步能力，全程遵循单向依赖、分层解耦的设计原则。
