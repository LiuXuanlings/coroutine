# MiniCyber 第二次重构验收与性能口径

> 本文件定义 MC-601~MC-623 的统一完成标准。任务卡说明“做什么”，本文说明“怎样证明已经做对”。不得使用旧 benchmark、测试数量或未归档日志替代本文要求的业务证据。

## 一、验收原则

1. 验收顺序为：静态边界检查 -> 高风险单元测试 -> 唯一主干集成测试 -> 文件级触达 -> Release 性能采集 -> 文档与 Git 收口。
2. 业务主干是最终判据；单元测试只用于隔离高风险底层错误。
3. Classic 与 Choreography 必须使用同一业务 DAG、相同业务输入和相同断言分别验收。
4. 测得事实与机制解释必须分开。没有数据不得写“提升 N 倍”“超低延迟”等结论。
5. 任何异常进程退出、超时、消息缺失、重复投递、SHM 残留或未触达生产文件都视为主验收失败。

## 二、平台与构建门禁

### 2.1 支持平台

- 操作系统：Linux
- 架构：x86_64
- 语言标准：C++17
- IPC：POSIX SHM
- 消息：Protobuf full runtime，公开 Channel 类型派生自 `google::protobuf::Message`
- 拓扑发现：系统 FastRTPS，仅同机控制面

不得把 aarch64、Windows、跨主机数据传输或 RTPS 数据面写入已支持能力。

### 2.2 CMake 门禁

| 配置 | 必须结果 | 用途 |
|---|---|---|
| Debug | 配置、编译成功 | 单元和集成调试。 |
| Release | 配置、编译成功且使用优化 | 性能采集。 |
| ASAN | 关键链可编译并运行 | 内存越界、UAF、泄漏检查。 |
| TSAN | 配置和关键目标可编译 | 支持宿主上运行；当前宿主若报地址映射限制必须保留原始证据。 |

CMake 必须显式列出生产源文件；FastRTPS 使用 `find_package(FastRTPS REQUIRED)`，缺失时应在配置期清晰失败，不允许自动下载或复制 `cyber_ref` 源码兜底。

### 2.3 静态黑名单检查

最终验收必须确认：

- 不存在 RPC `service/client` 生产文件或入口；
- 不存在 TimerComponent、TimingWheel、TimerComponentConfig、DAG timer_components；
- 不存在 talker/listener、旧 benchmark、C++20 coroutine 探针和旧采集脚本；
- 不存在 RtpsTransmitter、RtpsReceiver、RtpsDispatcher 和 RTPS 数据模式；
- 不存在 Component/DataVisitor/RoutineFactory 三、四输入生产路径；
- 不存在“工作窃取”“work-stealing”或跨组 Steal 的能力声明；
- 不存在普通 C++ 动态对象直接写入 SHM 的公开接口；
- 不存在旧性能 CSV/JSON 和英文性能报告。

## 三、高风险单元测试口径

只保留以下必要单测类别：

| 类别 | 必须验证的行为 |
|---|---|
| CRoutine ABI | x86_64 寄存器保存、栈对齐、双向 SwapContext、MainFunc shared_ptr 生命周期。 |
| CRoutine 状态 | DATA_WAIT/READY、完成、停止和重复 Resume 边界。 |
| Data | Dispatcher/Notifier 安全注销、AllLatest 主通道驱动、游标单次推进、填充先于唤醒。 |
| SHM | Protobuf 字节序列化/反序列化、块锁与引用、两种启动顺序、超过 1 KiB 动态字段、段不兼容失败、SIGINT/SIGTERM 后清理。 |
| Discovery | 双向 Join/Leave、SAME_PROC/DIFF_PROC、启动顺序、晚加入、显式 Leave、Participant 异常退出、回环去重、监听器并发注销和启动失败回滚。 |
| Hybrid | 纯 INTRA、纯 SHM、同一 Writer 混合订阅者并行扇出且无重复；回调内关闭端点不死锁。 |
| Classic | 同组 20 级共享队列、优先级、Acquire 防重复执行、关闭后清理。 |
| Choreography | 定向区、Classic 公共池、processor_id 越界拒绝和原路由唤醒。 |
| Component | 单/双通道 Proc 只在 Processor 协程执行，关闭后无回调。 |
| dlopen | 共享工厂注册、创建、失败回滚、Shutdown 和 dlclose 顺序。 |

建议 CTest 标签只保留 `unit`、`high_risk`、`cross_process`、`integration`。测试数量不是质量指标。

### 3.1 发现控制面专项门禁

1. Writer 必须观察到远端 Reader，Reader 也必须观察到远端 Writer；不能只验证单向状态。
2. 同进程角色为 `SAME_PROC`，同机跨进程角色为 `DIFF_PROC`。
3. 至少覆盖 Reader 先启动、Writer 先启动或晚加入重放，以及显式 Leave。
4. Participant 未发送 Leave 即退出时，远端最终清除其全部 Channel 角色。
5. 本地一次 Join/Leave 对 ChangeListener 精确产生一次事件；FastRTPS 回环不得重复通知。
6. RemoveChangeListener 与正在执行的回调并发时，返回后不得再访问监听器；回调抛异常
   不得破坏 in-flight 归还。
7. Participant、Type、Publisher 或 Subscriber 任一步启动失败都必须回滚已创建资源。
8. 跨进程测试只允许管道、事件、条件变量或有界状态条件编排，不允许固定 `sleep` 猜测
   发现完成。轮询只能用于带明确超时的业务条件，失败必须输出缺失角色或退出码。

## 四、唯一主干功能验收

### 4.1 固定运行参数

```text
--messages 1000 --frequency 100 --metrics
```

- 测量消息数：1000
- 发布频率：100 Hz
- 预期测量时长：约 10 秒，不含发现和预热
- 拓扑等待：有界超时，通过 Writer::HasReader/ChannelManager 判断，不使用固定 sleep
- AllLatest 预热：sequence 0 按 `VehicleState -> CameraFrame` 完整穿透五组件并由 Audit 回执，
  形成端到端屏障后再发布测量序列
- 测量发布顺序：每个序列先 VehicleState，后 CameraFrame

### 4.2 进程与加载断言

1. ControlSink、mainboard、SensorSource 是独立进程。
2. mainboard 读取唯一 `config/autodrive/autodrive.dag`。
3. module_library 非空，业务组件通过真实 `dlopen(RTLD_NOW | RTLD_GLOBAL)` 注册。
4. Perception、Fusion、Planning、Control、ControlAudit 均由 ComponentFactory 创建并初始化。
5. 两种调度运行只替换 Scheduler 配置文件，DAG 内容和业务输入保持一致。
6. 完成或失败后所有子进程均被回收，mainboard 通过 SIGTERM/SIGINT 优雅退出。

### 4.3 数据链断言

| 链路 | 预期后端 | 必须证明 |
|---|---|---|
| SensorSource -> Perception/VehicleState Reader | SHM | Protobuf 序列化跨进程恢复，序列和动态字段正确。 |
| Perception -> Fusion | INTRA | 同进程 shared_ptr 对象身份保持。 |
| Fusion -> Planning | INTRA | AllLatest 使用当前主输入和最新 VehicleState。 |
| Planning -> Control | INTRA | Trajectory 顺序和确定性字段正确。 |
| Control -> ControlAudit | INTRA | 本进程审计收到每条 ControlCommand。 |
| Control -> ControlSink | SHM | 同一 Writer 同时向外部进程发送，不影响本地 Audit。 |

### 4.4 协程链断言

至少通过可关闭的测试探针或结构化日志证明以下顺序：

```text
SHM/INTRA Receiver
  -> DataDispatcher::Dispatch
  -> ChannelBuffer::Fill
  -> DataNotifier::Notify
  -> Scheduler::NotifyTask
  -> CRoutine DATA_WAIT -> READY
  -> Processor::Run
  -> CRoutine::Resume
  -> SwapContext
  -> Component::Proc
```

发布线程 ID 不得等于 Proc 所在 Processor 线程 ID。关闭 metrics/trace 后不应保留逐消息调试开销。

### 4.5 业务结果断言

- ControlSink 收到完整 1000 条测量 ControlCommand；
- source_sequence 单调、无重复、无缺号；
- source_monotonic_ns 从 CameraFrame 贯穿到 ControlCommand，不被中间组件重置；
- Perception、Fusion、Planning、Control 的确定性数学结果与输入公式一致；
- ControlAudit 与 ControlSink 的序列集合一致；
- AllLatest 预热样本不进入最终性能样本；
- 任一阶段 Proc 返回失败时应有明确日志并触发可控退出，不得静默继续。

## 五、两种 Scheduler 验收

### 5.1 Classic

- 所有配置 group 均建立一组共享 20 级队列；
- 同组多个 Processor 竞争同一队列，而不是每 Processor 一个 `proc_i` 组；
- 高优先级 READY 协程先于低优先级被选择；
- Acquire 只防止重复执行，不存在跨组窃取；
- 数据到达唤醒所属 group；
- Shutdown 后静态组、等待计数和协程映射可被下一次运行重新创建。

### 5.2 Choreography

- 配置 processor_id 的高实时组件进入指定定向 Processor；
- 未配置 processor_id 的组件进入 Classic 公共池；
- 定向区和公共池在同一次业务运行中均被实际触达；
- 数据唤醒返回原定向 Processor 或原公共池；
- 非法 processor_id、空定向区或空公共池配置按 schema/运行要求明确拒绝，不静默降级。

## 六、发现与 Hybrid 验收

1. FastRTPS 仅发布/接收 Channel Join/Leave 控制消息。
2. 同主机不同 PID 被识别为 DIFF_PROC；同 PID 被识别为 SAME_PROC。
3. DIFF_HOST 不创建任何数据连接。
4. Writer::HasReader 在远端 Join 后变为 true，在全部 Reader Leave 后恢复 false。
5. 端点创建顺序不得改变最终路由；晚加入 Reader 必须触发 ChangeConnection。
6. 同一 ControlCommand Writer 同时存在本地 Audit 和远端 Sink 时，INTRA 与 SHM 连接并存。
7. 每个对端只通过一种数据后端接收，不能因 Hybrid 同时启用造成重复投递。
8. 构建目标、公开头文件和最终符号表不得包含 RTPS 数据收发类型。
9. 正式 Transport 工厂不得保留固定 INTRA 或非 Protobuf 泛型入口；底层收发器只作为内部实现和高风险测试边界。
10. Hybrid 状态锁内不得同步分发用户回调或等待在途回调；回调内关闭 Writer、Reader、Node 必须有界返回。
11. Protobuf SHM 必须覆盖 Reader 先启动、Writer 先启动和超过 1 KiB 动态字段；段布局不兼容时端点初始化必须失败。

## 七、生命周期与资源验收

- Component 关闭顺序：阻止新任务 -> 移除 Scheduler task -> 注销 Reader -> 释放业务 Writer/资源；
- ModuleController 关闭顺序：Shutdown 组件 -> 销毁组件 -> dlclose；
- mainboard 失败回滚只清理本次加载水位之后的资源；
- Discovery/Transport 关闭后不得再进入已卸载 `.so` 回调；
- POSIX SHM 块引用归零、段按所有权回收；
- 主干运行前后 `/dev/shm/minicyber_*` 无新增残留；
- SIGINT、SIGTERM 和子进程异常退出均有有界回收路径；单次退出信号在初始化期间、进入等待边界和已阻塞等待三种时机下均不得丢失，禁止“先检查标志、再无条件 pause”的非原子等待；
- 配置 CPU 亲和性时必须检查系统调用结果；宿主拒绝、CPU 不可用或目标线程已退出时必须有可诊断证据，不得静默宣称已绑核；
- ASAN 关键链无 UAF、double free、越界和可达泄漏增长。

## 八、100% 留存生产文件触达

### 8.1 定义

100% 指 MC-603 冻结的每个生产 `.h/.cpp/.S` 文件至少满足一个条件：

1. 被唯一主干可执行文件或核心库静态编译并在业务运行中执行其职责；
2. 被业务组件 `.so` 编译并由 mainboard 运行时加载执行；
3. 对模板头文件，由业务实例化和覆盖率/符号证据证明实例化路径被执行。

不要求 100% 行覆盖或 100% 分支覆盖，也不允许通过测试专用空调用伪造业务触达。

### 8.2 证据

- CMake 显式生产源清单；
- 可执行文件和 `.so` 链接/符号清单；
- Debug 覆盖率生成的文件级触达结果；
- mainboard 的 dlopen 模块清单；
- MC-619 在 `00_进度记录.md` 归档的逐文件结论。

未触达文件必须删除；若删除会破坏原生职责，应回到架构澄清，不能降低验收口径。

## 九、性能采集口径

### 9.1 唯一测量对象

只测完整自动驾驶主干，不再测 INTRA ping-pong、SHM ping-pong、PIPE、互斥队列或 C++20 coroutine。Classic 和 Choreography 是同一业务负载的两种配置结果，不预设优劣。

### 9.2 时间与样本

- SensorSource 在 CameraFrame 写入 `source_sequence` 和 `source_monotonic_ns`；
- 所有组件原样传递源字段；
- ControlSink 使用同一宿主 `CLOCK_MONOTONIC` 域计算端到端延迟；
- sequence 0 的 VehicleState 与 CameraFrame 必须完整穿透五组件并由 ControlAudit 回执形成
  端到端预热屏障；该样本和发现阶段不计入性能统计；
- 默认验收 1000 条可用于功能统计，不自动视为最终性能结论；
- 正式性能样本数可通过同一 Demo 参数扩大，但必须记录参数。

### 9.3 指标定义

| 指标 | 定义 |
|---|---|
| p50/p95/p99 | 完整 CameraFrame -> ControlCommand 端到端延迟分位数。 |
| 吞吐 | 从第一条测量结果到最后一条测量结果的成功消息数/秒。 |
| 丢包 | 期望 source_sequence 集合减去 ControlSink 实收集合。 |
| 重复 | 同一 source_sequence 在 ControlSink 出现超过一次。 |
| 审计一致性 | ControlAudit 与 ControlSink 的序列集合差异。 |
| 运行时长 | 发现完成后到最后结果接收的单调时间。 |

### 9.4 输出格式

CSV 至少包含：

```text
schema,commit,policy,messages,frequency_hz,samples,p50_ns,p95_ns,p99_ns,
throughput_msg_s,lost,duplicates,duration_ns
```

JSON 至少包含：schema、提交号、工作区状态、CPU 型号、在线 CPU 数、允许 CPU 列表、内核、编译器、构建类型、FastRTPS/Protobuf 版本、DAG Hash、Scheduler 配置、启动参数、指标和 SHM 回收结果。

### 9.5 性能运行规则

- 使用 Release 构建；
- 逐消息业务 evidence 默认关闭，只允许功能验收显式开启；性能运行仅开启 metrics；
- 最终性能数据必须来自代码、配置和采集脚本均已提交的干净工作区，JSON 的提交号必须
  对应实际运行二进制；dirty 数据只能标为临时观测；
- metrics 关闭时不维护延迟样本容器；
- 正常主干退出必须在兜底 `shm_unlink` 之前证明精确频道已自然回收；兜底清理只用于失败或中断后的环境恢复，不能作为生命周期验收证据；
- 每次结果保留原始 CSV/JSON，文件名区分 Classic 与 Choreography；
- 不挑选单次最好值，不隐去失败运行；
- 不与旧 benchmark 或 Apollo CyberRT 做数值横向比较；
- 报告必须区分“实际测得”与“由机制推断”。

## 十一、任务完成判定

单个任务只有同时满足以下条件才可标记“已完成”：

1. 只修改任务卡声明的所有权范围；
2. 任务产出可作为下一任务输入；
3. 任务卡要求的最小验证通过；
4. 重大问题已同步双手册；
5. 00 已记录验证与 Commit；
6. 创建单一 Commit 并推送 development。

最终 MC-623 只有在全部功能、资源、文件触达、性能、文档和 Git 门禁通过后才能完成。
