# 验收与性能口径

## 1. 功能验收

- Debug、Release 均能完成配置、编译和链接。
- ASAN 全量测试无内存错误；TSAN 在支持的平台完成重复运行并记录已知误报/限制。
- CTest 全量通过；压力测试、长时间稳定性测试、跨进程 SHM 测试均有独立命令和结果文件。
- talker/listener 与最小 DAG 可启动、通信、退出，异常加载能返回可诊断错误且不泄漏共享内存。
- Classic 与 Choreography 的关键状态、唤醒、关闭语义均有测试覆盖。

## 2. 性能实验设计

每次实验固定并记录：提交号、CPU/内核、编译器、构建类型、线程/进程数、消息大小、预热次数、测量次数、调度策略和系统负载。原始输出保存到 `docs/refactor/perf/`。

统一指标：单向延迟（p50/p95/p99、最小、最大）、吞吐（消息/秒）、端到端抖动、CPU 时间、上下文切换数、系统调用数、峰值 RSS、共享内存占用与失败/丢包计数。往返测试必须明确除以 2 的假设，不能与单向结果混表。

## 3. 对比基线

1. INTRA：MiniCyber 同进程发布订阅。
2. SHM：MiniCyber 双进程共享内存发布订阅。
3. PIPE：同消息规格的 POSIX pipe 基线。
4. 普通线程队列：互斥锁/条件变量保护的有界队列。
5. C++20 coroutine：独立实验目标，仅在编译器、实现和统计口径稳定时纳入；否则记录未纳入原因。

横向分析不只比较绝对延迟。每个基线都必须说明其适用场景和代价：INTRA 用于衡量同进程指针传递路径；SHM 用于衡量跨进程零拷贝与通知成本；PIPE 用于衡量内核态字节流 IPC；互斥锁/条件变量队列用于衡量传统线程同步；C++20 coroutine 用于比较语言级栈less协程与本项目栈式用户态协程在调度控制、取消、数据驱动唤醒和跨进程能力上的差异。不得把机制不同的基线仅按单一延迟排名。

实验矩阵至少覆盖：64 B、1 KiB、64 KiB 三档消息；单生产者单消费者与一生产者多消费者；空载与受控 CPU 竞争；Classic 与 Choreography；冷启动与预热后稳态。跨进程实验额外记录通知等待配置、复制次数和共享内存回收结果。稳定性实验至少记录连续运行时长、消息总数、错误数和资源增长曲线。

除基准数值外，报告应给出能力对照：内存复制路径、内核态切换、同步原语、背压/丢弃策略、调度可控性、部署边界、实现复杂度和适用负载。该对照用于解释项目的立项动因和差异化，不用于暗示未测得的性能结论。

不与 Apollo CyberRT 做运行时性能横向对比；项目与其源码关系仅通过架构映射和机制说明呈现。

## 4. 结论规则

不得预设“提升 N 倍”或使用单次最好结果。报告必须同时给出样本量、分位数、方差/置信区间（可行时）、失败实验和环境限制，并将“测得事实”和“机制推断”分开。
