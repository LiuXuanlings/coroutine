## 六、每任务证据包

每个 MC 任务完成时，必须在 00 历史记录中形成以下最小证据包：

```text
日期：YYYY-MM-DD
任务：MC-xxx
状态：已完成/阻塞
原生参考：cyber_ref/精确文件
改动文件：精确路径
设计结论：本任务对齐了什么，删除了什么
验证：实际命令、退出码和关键结果
资源检查：进程、线程、SHM、动态库等适用项
文档同步：DEBUG_MANUAL/INTERVIEW_QA 或“不适用及原因”
基线检查：Roadmap/00/04/05 同步结果；01/02/03 修改或不适用原因
代码注释：本任务新增/修改的 API、并发、所有权、回滚和关闭顺序检查
Commit：<完整 40 位 SHA> <subject>
Push：development 远端状态
阻塞或下一步：下一任务所需输入
```

禁止只写“测试通过”“代码已完成”或用计划命令冒充实际执行结果。

MC 生产任务 Commit 之后，如需把其最终 SHA 写回仓库，允许追加不带 MC 编号的纯台账
证据 Commit。该 Commit 只能修改基线文档中的 SHA、subject、Push 和远端状态，不得包含
生产代码、测试逻辑或下一任务内容；这是对“单任务单生产 Commit”的证据收口，不算新增 MC。

## 九、会话接力步骤

### 9.1 开始任务

1. 按路线图读取基线文档；
2. 从 00 获取唯一当前任务；
3. 核对上一步产出已经存在；
4. 阅读任务卡列出的全部精确源码；
5. 回报前序输入、原生职责映射和验证门禁；
6. 将任务状态改为“进行中”并提交或纳入当前任务提交；
7. 只执行该任务。

### 9.2 结束任务

1. 执行任务卡最小验证；
2. 增量更新 INTERVIEW；重大排错按完整时间线更新 DEBUG；
3. 检查关键意图注释和原生职责映射；
4. 同步 Roadmap、00、04、05，并检查 01/02/03；
5. `git diff --check` 并核对暂存路径；
6. 创建一个任务 Commit并推送 development；
7. 记录完整 40 位 SHA，确认 HEAD 与 `origin/development` 一致；
8. 确认 00 指向下一未完成任务。

### 9.3 遇到阻塞

只有以下情况标记阻塞：外部依赖缺失、原生源码与定稿决策不可兼容、任务所有权出现无法拆分的循环、同一环境问题重复且无安全替代。记录证据后停止，不得通过自创实现绕过。

## 十、禁止复用的旧宣传口径

- Classic 工作窃取、每核私有队列；
- Choreography 抛弃所有优先级队列或按 DAG 边 O(1) 直接唤醒；
- SHM 对普通 C++ 动态对象直接零拷贝；
- INTRA/SHM/RTPS 三级数据路由；
- 自动 Transport 永久固定 INTRA；
- TimerComponent 属于最终主干；
- 自研 RPC 属于项目亮点；
- 旧 PIPE/C++20/互斥队列 benchmark 证明性能优势；
- 未实测的“提升 N 倍”“工业级”“极限无锁”等结论。
