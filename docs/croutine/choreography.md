# ChoreographyContext 技术设计与实现说明文档
## 一、文档概述
本文档用于讲解 minicyber 调度框架中 `ChoreographyContext` 的设计思路、实现细节与使用约束。

`ChoreographyContext` 是 minicyber 调度系统中**编排调度模式**的核心上下文类，继承自 `ProcessorContext` 抽象基类，负责管理单调度路径下的协程就绪队列、提供协程获取与阻塞唤醒能力，语义对齐 Apollo CyberRT 原生 `choreography_context`。

其核心设计目标是：面向自动驾驶 DAG（有向无环图）依赖触发场景，提供低延迟、高确定性的协程调度能力。

## 二、设计背景与选型依据
### 2.1 传统 ClassicContext 的场景痛点
ClassicContext 采用「多级优先级队列 + Work-Stealing（任务窃取）」的通用调度架构，存在以下适配性问题：
- Processor 空闲时需扫描所有优先级队列筛选就绪协程，开销随队列长度线性增长
- 自动驾驶业务中大量协程长期处于 `DATA_WAIT` 等待态，无效扫描占比极高
- 跨 Processor/跨 Group 的任务窃取机制会带来缓存失效、调度延迟波动等问题

### 2.2 编排调度的场景适配
自动驾驶核心业务链路（感知→预测→规划→控制）是典型的**依赖驱动型 DAG 模型**，具备以下特征：
- 协程（计算节点）的触发由上游数据就绪决定，属于「定向点对点唤醒」
- 链路优先级明确，高优先级任务需严格保障调度时序
- 协程与 Processor 绑定关系稳定，无需动态负载均衡
- 调度延迟敏感，要求调度路径开销尽可能低

基于以上场景特征，`ChoreographyContext` 采用「单一优先级就绪队列 + 显式入队」的设计，移除全局扫描与任务窃取逻辑，专为依赖触发型 DAG 调度做定向优化。

## 三、核心数据结构与成员说明
`ChoreographyContext` 所有成员均为实例级别，无静态共享变量，保证不同上下文实例完全隔离。成员分为两大模块：阻塞唤醒模块、就绪队列管理模块。

### 3.1 阻塞唤醒模块
用于实现 Processor 空闲时的挂起与任务唤醒，基于条件变量实现可靠阻塞机制。

| 成员变量 | 类型 | 核心作用 |
|---------|------|----------|
| `mtx_wq_` | `std::mutex` | 保护唤醒计数与条件变量的互斥锁，保证并发操作线程安全 |
| `cv_wq_` | `std::condition_variable` | 阻塞等待的条件变量，实现线程的挂起与唤醒 |
| `notify_` | `int` | 唤醒计数器，配合条件变量规避虚假唤醒、避免唤醒丢失，实现「多次 Notify 对应多次 Wait 消费」的语义 |

### 3.2 就绪队列管理模块
核心是优先级就绪队列与读写锁，负责协程的存储、排序与并发访问保护。

| 成员变量 | 类型 | 核心作用 |
|---------|------|----------|
| `rq_lk_` | `AtomicRWLock` | 原子读写锁，分离读写场景：<br>- 读路径（`NextRoutine`）加读锁，支持多线程并发访问<br>- 写路径（`Enqueue`/`Remove`）加写锁，保证修改操作原子性 |
| `cr_queue_` | `std::multimap<uint32_t, std::shared_ptr<CRoutine>, std::greater<uint32_t>>` | 优先级就绪队列：<br>1. 以协程优先级为 key，`std::greater` 排序保证 `begin()` 直接指向最高优先级<br>2. `multimap` 特性保证同优先级协程按插入顺序排列（FIFO）<br>3. 存储 `shared_ptr` 保障协程对象生命周期安全 |

> 补充：`stop_` 继承自基类 `ProcessorContext`，为原子布尔值，标记上下文是否停止调度。

## 四、核心接口实现深度解析
### 4.1 NextRoutine：获取下一个就绪协程
**接口语义**：从就绪队列中取出最高优先级的就绪协程，返回给 Processor 执行；无就绪协程时返回 `nullptr`。

**执行流程**：
1. **停止校验**：若 `stop_` 为 `true`，直接返回 `nullptr`，终止调度。
2. **加读锁**：通过 `ReadLockGuard` 持有队列读锁，支持多 Processor 并发取任务。
3. **优先级遍历**：从队列头部（最高优先级）开始逐个检查协程：
   - 调用 `Acquire()` 尝试占用协程执行权，失败则说明协程正被其他线程执行，直接跳过。
   - 调用 `UpdateState()` 刷新协程状态，将满足唤醒条件的 `DATA_WAIT`/`IO_WAIT`/`SLEEP` 状态转为 `READY`。
   - 若状态为 `READY`，直接返回该协程（调用方执行完成后必须调用 `Release` 释放执行权）。
   - 若协程非就绪，调用 `Release()` 释放执行权，继续遍历下一个。
4. 遍历结束未找到就绪协程，返回 `nullptr`。

**设计要点**：
- 热路径优化：`NextRoutine` 是调度核心热路径，全程读锁操作，无写锁开销，延迟稳定可控。
- 状态二次校验：先占用再校验状态，避免状态变更的竞态问题，保证协程执行唯一性。
- 惰性清理策略：已结束（`FINISHED`）的协程仍保留在队列中，避免在热路径执行写锁删除操作。

### 4.2 Enqueue：协程显式入队
**接口语义**：将协程定向加入本上下文的就绪队列，由上游依赖满足后触发调用（如 `Scheduler::NotifyTask`）。

**执行流程**：
1. 空指针合法性校验，无效指针返回 `false`。
2. 加写锁：通过 `WriteLockGuard` 持有队列写锁，保证插入操作线程安全。
3. 按优先级插入：调用 `emplace` 将协程按优先级插入 `multimap` 对应位置，同优先级保持插入顺序。
4. 解锁后调用 `Notify()` 唤醒阻塞等待的 Processor，保证新任务被及时调度。

**设计要点**：
- 点对点定向入队：协程仅在依赖满足时才进入就绪队列，队列中绝大多数为就绪态协程，大幅降低无效遍历开销。
- 入队即唤醒：最小化任务从入队到被调度的延迟，适配实时性要求高的业务场景。

### 4.3 Wait / Notify：阻塞与唤醒机制
#### Notify
**接口语义**：唤醒一个阻塞在 `Wait()` 的 Processor。
实现逻辑：加锁将 `notify_` 计数 +1，随后调用 `cv_wq_.notify_one()` 唤醒单个等待线程。

#### Wait
**接口语义**：队列为空时，Processor 调用此接口阻塞挂起，直到有新任务入队或上下文停止。

**执行流程**：
1. 持有互斥锁，调用 `wait_for` 阻塞等待，兜底超时时间设为 1 秒。
2. 唤醒条件为 `notify_ > 0`，从机制上规避条件变量的虚假唤醒问题。
3. 被唤醒后，若 `notify_ > 0` 则将计数 -1，消费一次唤醒事件。

**设计要点**：
- 计数型唤醒：通过计数器保证唤醒不丢失，多次 Notify 可对应多次 Wait 消费。
- 1秒超时兜底：防止极端场景下唤醒计数丢失导致线程永久阻塞，属于容错设计；每秒一次的假唤醒对系统性能影响可忽略。

### 4.4 Shutdown：停止上下文
**接口语义**：终止上下文调度能力，唤醒所有阻塞等待的线程。

**执行流程**：
1. 原子设置 `stop_` 为 `true`，后续 `NextRoutine` 直接返回 `nullptr`，不再调度新任务。
2. 加锁将 `notify_` 设为 `int` 类型最大值，保证所有等待线程都能消费到唤醒事件。
3. 调用 `notify_all()` 唤醒所有阻塞在 `Wait()` 的线程，确保所有 Processor 正常退出。

### 4.5 RemoveCRoutine：移除指定协程
**接口语义**：按协程 ID 从队列中移除协程，通常用于协程销毁、组件卸载等场景。

**执行流程**：
1. 加写锁，遍历队列查找对应 ID 的协程。
2. 找到后调用 `cr->Stop()` 将协程标记为 `FINISHED`，防止 `NextRoutine` 再次选中该协程。
3. 自旋调用 `Acquire()` 直到成功：确保当前正在执行该协程的 Processor 已执行完毕并释放执行权，避免 use-after-free 内存错误。
4. 从队列中 `erase` 该协程节点。
5. 调用 `Release()` 释放本次占用的执行权；局部 `shared_ptr` 析构后，协程对象生命周期由外部持有者管理。

**关键安全设计**：
- 必须拷贝 `shared_ptr`：遍历过程中用局部变量拷贝协程的智能指针，而非直接使用引用。因为 `erase` 会销毁 `multimap` 节点内的 `shared_ptr` 对象，若使用引用，`erase` 后引用会变成悬垂引用，后续调用 `Release()` 会触发内存访问错误。
- 自旋等待执行结束：保证协程被移除时没有正在执行的代码路径，从根源避免野指针与资源泄漏。

## 五、关键设计决策与权衡分析
### 5.1 读写锁 vs 互斥锁
- **选型**：采用 `AtomicRWLock` 读写锁保护队列
- **背景**：调度场景中 `NextRoutine` 调用频率远高于 `Enqueue` 和 `Remove`，属于典型读多写少场景
- **收益**：读锁可重入，多 Processor 并发取任务时无锁竞争，大幅提升热路径吞吐量
- **代价**：写锁需要等待所有读锁释放，写操作延迟略高于互斥锁；但写操作频率低，整体收益远大于代价

### 5.2 惰性清理 vs 即时清理
- **选型**：`FINISHED` 协程惰性清理，仅显式调用 `RemoveCRoutine` 时移除
- **背景**：若在 `NextRoutine` 中即时删除已结束协程，需要将读锁升级为写锁，破坏读路径的并发性能
- **收益**：调度热路径全程读锁，无写操作，延迟稳定可控
- **代价**：队列中会残留已结束的协程，占用少量内存；在 DAG 场景下协程数量固定、生命周期长，该代价可忽略

### 5.3 无任务窃取 vs 负载均衡
- **选型**：不支持 Work-Stealing，实例间完全隔离
- **背景**：编排调度模式下，协程与 Processor 静态绑定，任务由上游定向分发到指定 Context，负载均衡由上层 DAG 划分保证
- **收益**：无跨核任务迁移开销，Processor 缓存亲和性好，调度延迟可预测
- **代价**：单个 Processor 负载过高时无法从其他 Processor 窃取任务，极端场景下资源利用率略低

### 5.4 单队列优先级排序 vs 多优先级队列
- **选型**：单个 `multimap` 按优先级排序
- **背景**：编排模式下就绪协程数量少，单队列维护成本低
- **收益**：实现简洁，取最高优先级元素为 O(1)，内存布局紧凑
- **代价**：插入操作复杂度为 O(log n)，但插入频率低，对性能影响可忽略

## 七、使用约束与注意事项
### 7.1 生命周期契约
- 调用 `NextRoutine` 获取协程后，执行完成必须调用 `cr->Release()` 释放执行权，否则该协程将永远处于占用状态，无法被再次调度。
- 协程生命周期结束后，需显式调用 `RemoveCRoutine` 从队列中清理，避免内存残留。

### 7.2 并发安全约束
- `Enqueue`、`RemoveCRoutine` 为写操作，持有写锁期间会阻塞所有读操作，应避免在高频热路径调用。
- `RemoveCRoutine` 中的自旋等待会持续占用写锁，若协程执行时间过长，会导致整个队列长时间不可写；需保证协程执行体的执行时间可控。

### 7.3 状态语义约束
- 协程入队前不强制要求为 `READY` 状态，`NextRoutine` 会通过 `UpdateState` 动态刷新；但建议仅在依赖满足时入队，减少无效遍历。
- `Shutdown` 仅停止调度能力，不会自动销毁队列中的协程对象，协程的内存回收由外部 `shared_ptr` 持有者管理。

### 7.4 常见踩坑点
- 禁止在持有读锁期间调用写操作，会造成死锁。
- 移除协程时禁止直接保存队列元素的引用，必须拷贝 `shared_ptr`，否则 `erase` 后会触发悬垂引用。
- 不要依赖同优先级协程的绝对执行顺序，`multimap` 的等价键顺序仅在单线程入队时保证 FIFO，并发入队场景下顺序不可预测。

## 八、与 ClassicContext 对比
| 对比维度 | ChoreographyContext | ClassicContext |
|---------|---------------------|----------------|
| 队列结构 | 单 multimap 优先级队列 | 多级优先级队列 |
| 任务入队 | 上游显式点对点入队 | 协程创建后全局入队 |
| 任务窃取 | 不支持，实例完全隔离 | 支持跨 Processor/Group 窃取 |
| 取任务开销 | 近似 O(1)，就绪态占比高时几乎无无效扫描 | O(n)，需扫描所有队列并跳过等待态 |
| 等待态处理 | 仅就绪协程入队，无无效扫描 | 等待态协程留在队列中，每次扫描均需跳过 |
| 适用场景 | DAG 依赖触发、优先级明确、延迟敏感的业务链路 | 通用计算、负载均衡要求高的场景 |
| 锁机制 | 读写锁，针对读多写少优化 | 互斥锁保护队列操作 |

## 九、总结
`ChoreographyContext` 是面向自动驾驶 DAG 调度场景的定向优化实现，核心设计思路是「用场景约束换性能」——通过移除通用调度的复杂能力（全局扫描、任务窃取），换取更低、更稳定的调度延迟，是 minicyber 调度系统中实现确定性调度的核心组件。
